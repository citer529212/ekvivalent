# Вход по телефону: Supabase + SMS.ru

Статус: клиент и серверный обработчик подготовлены. Для реальных SMS владелец должен выполнить SQL, развернуть функцию и настроить секреты/Hook в своём Supabase. Само добавление файлов в GitHub не подключает отправку SMS.

## 1. Лимиты

В SQL Editor выполнить `supabase/sms-budget.sql`. Он создаёт закрытый журнал в схеме `ekvivalent_private`, RPC только для server-side service_role и начальные лимиты: 10 попыток отправки за сутки, 3 на номер. Неудачные попытки тоже учитываются; повтор уже отправленного webhook-id не отправляет SMS повторно. Номера хешируются, коды SMS в журнал не записываются. В Supabase Phone/Rate Limits оставить серверное ограничение частоты OTP не меньше 60 секунд.

Лимит — в количестве попыток, а не в рублях. Стоимость сообщения и баланс определяет SMS.ru. Повышение лимитов выполнять осознанно после проверки доставки. Первая версия ограничена российскими мобильными номерами `+7 9…`.

## 2. Серверная функция

В Supabase открыть Edge Functions → Deploy a new function → Via Editor. Создать функцию `ekvivalent-send-sms` и вставить весь файл `supabase/functions/ekvivalent-send-sms/index.ts`. В настройках этой функции отключить платформенную проверку JWT (**Verify JWT / Enforce JWT verification**): входящий запрос проверяется собственной HMAC-подписью Auth Hook. Без действительной подписи код не отправляет SMS.

Адрес функции для этого проекта:

`https://dwrvlbindrscaxcmteoz.supabase.co/functions/v1/ekvivalent-send-sms`

CLI-альтернатива для владельца с настроенным Supabase CLI:

```
supabase functions deploy ekvivalent-send-sms --no-verify-jwt
```

Секреты никогда не добавлять в GitHub или `account-config.js`.

## 3. Секрет SMS.ru

В кабинете SMS.ru открыть «Программистам» и найти свой API_ID. В Supabase → Edge Functions → Secrets добавить:

- Name: `SMS_RU_API_ID`
- Value: действительный API_ID из личного кабинета SMS.ru.

Пароль от SMS.ru сюда не подходит. Не присылать ключ в чат и не показывать его на скриншотах.

## 4. Подписанный Auth Hook

В Authentication → Auth Hooks добавить **Send SMS**, тип **HTTP**, с адресом функции из шага 2. Сгенерировать signing secret. В Edge Functions → Secrets добавить:

- Name: `SEND_SMS_HOOK_SECRET`
- Value: signing secret из настроек этого Send SMS Hook (включая префикс `v1,whsec_`, если показан).

Сохранить и включить Hook. Не отправлять secret в чат. Функция использует встроенные серверные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`: не переносить service_role в клиент.

## 5. Включение телефона

После настройки Hook открыть Authentication → Sign In / Providers → Phone. Включить Phone Provider. Подтверждение номера оставить включённым; не использовать автоматическое подтверждение и общедоступные тестовые коды. Когда Hook включён, он заменяет встроенного SMS-провайдера: отдельная учётная запись Twilio не нужна. Если панель требует чужие ключи провайдера, проверить, сохранён ли Send SMS Hook, и обновить страницу; не вставлять выдуманные credentials.

## 6. Проверка

На сайте открыть «Аккаунт» → «По телефону» → «Создать аккаунт», ввести своё имя и российский мобильный номер. Запросить один код, проверить SMS и войти. Создание сессии выполняется только `/auth/v1/verify`, после проверки кода службой Supabase. Затем ответить на несколько вопросов, дождаться синхронизации и проверить вход с другого устройства.

Почта остаётся отдельным способом входа. Новый аккаунт по номеру автоматически не объединяется с прежним аккаунтом по почте. Коды и черновик номера не включаются в локальный прогресс или JSON-экспорт.

## Проверки реализации

- `node check-phone.cjs`: нормализация номера, блокировка неподключённого провайдера, регистрация/вход, неверные коды, повтор, изоляция аккаунта, отсутствие сохранённых OTP.
- `node check-sms-hook.mjs`: подпись, время запроса, изменение тела, ограничения страны, бюджет, повтор webhook, ответ SMS.ru по конкретному номеру, отсутствие OTP в журнале бюджета. Запросы SMS.ru моделируются; платные сообщения тестами не отправляются.
- `node check-account.cjs`, `node check.cjs`, `node check-listening.cjs`: существующие сценарии.

Доставка на реальный телефон проверяется отдельно после подключения владельцем. SQL нужно успешно выполнить в реальном Supabase; unit-тесты не заменяют проверку схемы и RPC в Postgres.
